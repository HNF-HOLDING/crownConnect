# CrownConnect AWS migration

This CloudFormation foundation creates the first deployable AWS service layer in `af-south-1`:

- Amazon RDS PostgreSQL for accounts, salons, bookings, services, and products.
- Amazon S3 for portfolio photos and videos.
- Amazon Cognito for customer and seller sign-in.
- Amazon API Gateway and Lambda. `GET /health` is a safe smoke-test endpoint.
- A private VPC, database subnets, security groups, and Secrets Manager credentials.

The current application runs as a Cloudflare Worker and uses Cloudflare D1/R2 and ChatGPT sign-in. The live public website stays in place during migration. Its booking, seller, account and upload routes still need to move to the new PostgreSQL/S3/Cognito API before the frontend can point at AWS.

## First deployment

Deploy `template.yaml` in AWS CloudFormation in **Africa (Cape Town)**. The stack creates the AWS foundation and exposes an API URL; open `API_URL/health` and expect a JSON `status: ok` response. The database password is generated in Secrets Manager, never entered in the template or committed to this repository.

This first deployment includes an RDS PostgreSQL instance and therefore has an ongoing AWS cost. It deliberately does **not** switch the public website to AWS yet.

## API conversion package

`api/` contains the production Lambda implementation for the first customer-facing API slice: stylist discovery, stylist details/services, booking availability, account roles, and booking requests. It uses the RDS secret generated by the stack rather than storing a password in source code.

Before updating the Lambda function, package `api/` and upload `dist/crownconnect-api.zip` to the `MediaBucketName` output under `deployments/crownconnect-api.zip`. The next CloudFormation update switches the inline health-check function to that uploaded package and adds authenticated routes.

## Database conversion

`db/001_crownconnect_schema.sql` is the PostgreSQL schema for the AWS RDS database. It preserves the live application's account, customer application, salon, service, portfolio media, and booking data model, including the active-booking slot rule.

After RDS is created, run this migration once through a private database connection. Set the resulting AWS identifiers and database connection string in the Lambda environment using `aws/.env.example` as the key list. Do not commit real credentials.

Do not deploy `template.yaml` until the Lambda application package and private VPC/database networking are added. The RDS resource is deliberately private and needs subnet/security-group configuration before production deployment.
